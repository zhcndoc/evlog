# 表面：技能

两组技能，它们不是同一个产品。

- `.agents/skills/` 是内部技能。它由在此代码库中工作的代理加载，可以假设检出目录、命令和约定都存在。
- `apps/docs/skills/` 是已发布的技能，通过文档站点下的 `.well-known/skills` 提供。它由其他代码库中的其他代理加载，并将 evlog 作为依赖使用。

为其中一方编写的技能如果被移到另一方，在两个方向上都是错误的：内部技能会泄露代码库路径，已发布的技能则会对它本应了解的代码库含糊其辞。

## 它对读者的要求

它的读者是一个正在处理任务且预算有限的模型。它应按以下顺序提供：

1. 一个能在正确情境下触发、在其他情况下保持安静的 `description`。
2. 按执行顺序排列的步骤，并将命令作为命令提供。
3. 边界：它绝不会做什么，以及哪些事项应交由人工处理。

只有当某个步骤看起来不合理、代理很可能会主动跳过时，理由才值得保留。

## 这里真正起作用的规则

- **M-06** 决定文件是否会被加载。无人加载的技能不是文档问题，而是死文件。
- **M-03** 和 **M-07** 决定技能在加载后是否值得信任。在同一轮检查中，验证每个路径与检出目录是否一致。
- **M-09** 决定谁可以修改它。修正措辞可以，修改步骤不可以。
- **U-15** 需要严格执行：教代理使用错误的排水口术语的技能，会产生使用错误术语的 PR。

## 内容检查会检查什么

- 代码库是否仍然具有技能所描述的布局？`AGENTS.md` 列出了内部技能及其主题；涵盖适配器、增强器或集成的技能如果所针对的对象已经改变形态，就必然已经过时。
- 已发布的技能是否仍然匹配软件包的公共 API？它们是作为依赖读取 `evlog` 的，因此入口点重命名会悄无声息地破坏它们。
- 两组技能是否相互矛盾？同一主题却有两套步骤，这对双方都是一个问题。
