# 选择能力在 Evi 中的归属位置

Evi 是一个垂直领域代理：一个领域（evlog）、一个代码仓库、一个维护者。
目前根目录界面承载所有内容，并且在当前规模下这是正确的。随着规模增长，
保持界面可读性的关键在于*如何*表达每项能力。

添加新能力时，请按以下顺序确定其位置：

1. 如果模型只需要一个可选的流程来实现它已有的能力，请编写一个**技能**
   (`agent/skills/<id>/SKILL.md`)。成本最低，无需代码。
2. 如果工作必须按固定周期启动，请添加一个**计划任务**（`agent/schedules/`），
   将提示发送到正确的频道；提示中的流程应放在代理加载的技能中，而不是计划任务文件里。
3. 如果该能力是模型应直接调用的远程 API，优先使用一个**连接**
   (`agent/connections/`)，并配合明确的 `tools.allow` 列表，而不是手写 fetch 工具。
4. 仅当操作需要连接无法表达的 Evi 端逻辑时，才编写一个自定义**工具**
   (`agent/tools/`)：凭据代理、门控、响应整形。使用 `defineDynamic` +
   `agent/lib/trust.ts` 控制可见性，而不要只在 `execute` 内部进行检查。
5. 只有在满足下方触发条件时，才考虑使用**子代理**。不要为了让目录树看起来更整洁而创建子代理。

## 两层规则

`agent/` 下除 `agent/lib/` 之外的每个代码文件都是连接层：它声明一个频道、工具、计划、指令片段或连接，并从 `agent/lib/` 导入其逻辑。技能（`agent/skills/*/SKILL.md`）和核心的 `instructions.md` 是编写的说明文本，而不是代码；它们存放在 eve 能发现的位置，并且没有对应的 `agent/lib/` 文件。逻辑位于 `agent/lib/<domain>/` 中（如果某个领域只有一个文件，也可以使用扁平模块），由小型的单一职责函数组成，每个函数都与一个同目录的 `*.test.ts` 文件配套。某个模块会一直保持扁平结构，直到其领域拥有第二个文件；届时该领域会获得一个目录（`agent/lib/github/` 就是第一个）。

权限只在 `agent/lib/trust.ts` 中定义一次（`isMaintainer`、`isAutonomous`、`canAccessAdminTools`），并在其他所有地方引用。新的能力绝不能自行发明调用方检查。

## 说明

`agent/instructions.md` 仅包含每个会话都需要的内容：身份、语气、检索规则、响应深度。任何取决于频道或调用者状态的内容，都是位于 `agent/instructions/*.ts` 中的动态片段（`workspace.ts`、`first-responder.ts`），会在 `turn.started` 时注入。如果核心文件中的某个章节以“在此频道中”或“无人值守时”开头，则该章节应属于一个片段。

## 子代理变得合理的时机

触发条件是实际观察到的，而不是为了美观：交互式 GitHub、Slack 或 iMessage 会话由于深入的代码仓库研究（为了回答一个问题而读取数十个文件）共享其上下文，导致输入令牌数激增或丢失上下文。此时，添加一个本地的 `repo-research` 子代理：使用隔离的上下文，仅使用沙箱文件工具，可选择使用更便宜的模型，并返回综合后的答案。Evi 的其他路由不变。

第二个、较晚出现的触发条件是独立的权限边界：某项能力的凭据、
故障模式或发布节奏不应随 Evi 一起变化。目前不存在这样的能力。

第三个触发条件现在已经在使用中，这也是内容处理流程遇到的触发条件：某项任务的正确性取决于双方不能共享上下文。`content_review` 和 `content_rewrite` 作为独立的子代理存在，因为能够编辑的审阅者会设法说服自己进行无法证明合理的修改，而读过审阅者推理过程的写作者会根据该推理重写，而不是根据页面重写。对话隔离使角色彼此分离。`agent/lib/content-sandbox.ts` 通过 eve 的回调 API 明确选择 `parent.sandbox`，因此两个代理都能读取父代理的分支和未提交页面，而无需克隆另一个检出版本。它们不得添加沙箱种子或打包技能，因为 eve 不允许在共享工作区中这样做。父代理通过 `content_snapshot` 捕获页面身份；子代理使用 `content_load` 验证其摘要和源提交。两个工具都是只读的。写作者返回拟议文本及其输入身份。父代理等待读取者完成，再次检查该身份，并使用现有编辑工具按顺序应用经过审阅的更改。随后它捕获已保存的文件，并在发布前请求新一轮审阅。这些指令负责协调 Evi 的编辑；快照检查并不会使写入操作相对于另一个进程变得原子化。并发外部编辑要求在 Evi 继续之前进行协调。不引入自定义写入事务或持久锁。逻辑和本地 Git 回归测试位于 `agent/lib/content/handoff.ts` 及其同目录测试中，其中包括在父代理编辑后拒绝过期快照。`content-sandbox.test.ts` 验证两个声明的代理都会选择父代理。它们的 shell 和文件写入工具已禁用；`glob`、`grep` 和 `read_file` 支持源代码检查。父代理执行示例并应用重写。扫描有 30 秒的截止时间，即使没有 shell 退出事件到达，也会通过沙箱文件 API 清理其暂存段落。如果扫描和清理都失败，聚合错误会保留这两个失败以及原始原因。可执行评估 fixture 会在子进程中运行，超时时间为 10 秒，并会被强制终止。

## Review checklist

添加功能前，请在 PR 中回答：

1. 技能、计划、连接、工具还是子代理——以及为什么不选择上方成本更低的那个？
2. 适用哪个 `trust.ts` 门控，以及自主回合会看到什么？
3. 逻辑位于 `agent/lib/` 中的什么位置，其测试位于何处？
4. 哪个技能或指令片段记录了该功能，并在同一个 PR 中更新？
