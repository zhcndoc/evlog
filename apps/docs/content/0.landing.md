#headline
常见问题
#title
安装之前
#body
  ::accordion{type="single"}
    ::accordion-item{label="我已经在使用 pino。实际会发生什么变化？"}
    evlog 提供上下文累加器和用于完成请求事件的集成。`log.set()` 会在操作期间向事件添加字段，而发出的事件会同时携带其结果和错误。Pino 也可以一次性发出一个已完成的对象，累加过程则由你的应用管理。`createError()` 会添加 `why` 和 `fix`，而[目录](/learn/catalogs)则为重复出现的失败提供稳定代码。调用签名、序列化器和输出配置需要进行明确迁移。请参阅[针对你的堆栈的比较](/reference/vs-other-loggers#choose-the-comparison-for-your-stack)。
    ::
    ::accordion-item{label="我的应用已经在生产环境中运行了。现在开始是不是太晚了？"}
    不晚，而且你不必猜从哪里开始。`evlog map` 会读取你的源代码，根据每个入口点在发生故障时能够提供给你的上下文进行评分，然后列出优先修复的入口点。它不需要流量、代理或部署，因此你可以在下一次事故发生之前，而不是事故处理中，获得这份清单。无论是上线第一天还是第三年，需要做的工作都是同一份清单。请参阅[如何将它添加到已经在生产环境中运行的应用](/cli/map#adding-it-to-an-app-already-in-production)。
    ::
    ::accordion-item{label="我必须改变日志的发送位置吗？"}
    不需要，你可以继续使用已经付费的平台。evlog 负责生成事件，排水管道负责发送它们：Axiom、Datadog、Sentry、Better Stack、PostHog、Loki、ClickHouse、OTLP 或文件系统。更换提供商只需替换排水管道，而不是改变架构，因为你的处理程序从未指定目标位置。如果你是在构建平台而不是购买平台，那么同一条管道也正是你接入的位置。请参阅[排水管道如何让目标位置不出现在你的代码中](/integrate/adapters/overview#send-events-without-naming-a-destination-in-your-code)。
    ::
    ::accordion-item{label="将这些日志发送出去会花费更多吗？"}
    通常花费更少。在[日志成本指南](/reference/cost)中，对于结账场景，一个请求会产生一个事件而不是四行日志，测得的结果是**字节数减少 56%，事件数减少 75%**，因为级别、时间戳、主机和请求绑定不再在每一行中重复。最终账单受这两个数字中的哪一个影响，取决于你的提供商：大多数提供商按摄入的 GB 收费，因此你会节省字节数；而同时按每百万个已索引事件收费的提供商，则会因事件数量减少而降低费用。然后，[采样](/learn/sampling)会丢弃你本来不会读取的内容，并强制保留错误和慢速请求。请在[哪个数字会影响你的账单](/reference/cost#which-number-moves-your-bill)中根据你自己的流量计算价格。
    ::
    ::accordion-item{label="采用它需要多少工作量？"}
    你可以一次迁移一个处理程序。有两个调用值得学习：`log.set()` 会向正在处理的事件添加上下文，`createError()` 则会为错误附加 `why` 和 `fix`，而不是只有一个裸堆栈。请参阅[第一天需要使用其中多少内容](/start/quick-start#how-much-of-this-do-you-need-on-day-one)，如果你想先了解其形态再看代码，也可以参阅[evlog 是什么](/start/introduction)。
    ::
    ::accordion-item{label="它在运行时的成本是多少？"}
    核心包**没有运行时依赖**。执行成本取决于上下文大小、脱敏、输出和交付方式。静默构造基准测试不包括控制台序列化和远程导出，因此无法确定每个生产请求的固定成本。请按照[一次真实请求的成本](/reference/performance#what-it-costs-on-one-real-request)，在你的运行时环境中测量完整路径。
