evlog 的审计层**不是一个并行系统**。审计事件是带有保留 `audit` 字段的宽事件。每个现有的基础组件（排出器、enricher、redact、tail-sampling）都可以照常使用。只需添加 **1 个 enricher + 1 个排出器包装器 + 1 个辅助函数**，即可启用审计日志。

在 evlog 之上为我的应用添加一份可防篡改的审计日志。

- 识别我的框架，并遵循其 evlog 集成模式
- 在 evlog:enrich 钩子上注册 auditEnricher()（或者在 initLogger.enrichers 中注册）
- 在主排出器旁边，注册一个独立的 auditOnly(signed(createFsDrain({ dir: '.audit' }), { strategy: 'hash-chain' })) 排出器
- 在审计排出器上使用 { await: true }，以确保审计事件在响应返回前被刷新
- 对每个安全敏感操作都调用 log.audit({ action, actor, target, outcome, reason })（登录、角色变更、退款、数据导出、删除）
- 审计事件会强制保留，跳过采样，并通过哈希链签名以实现防篡改证明
- 与 Better Auth 集成结合后，actor.id / actor.email 会自动填充

文档：https://www.evlog.dev/use-cases/audit/overview
适配器：https://www.evlog.dev/integrate/adapters/overview


查看 [智能体技能](/reference/agent-skills) 以获取完整列表。仓库中的技能路径：`skills/build-audit-logs`、`skills/analyze-logs`。

## 为什么需要审计日志？

合规框架（SOC2、HIPAA、GDPR、PCI）要求知道**谁在什么时间、从哪里、对哪个资源、做了什么，以及结果如何**。evlog 无需第二个日志库就能覆盖这一需求。

::tip
**审计事件是关于意图的事实，而不是对操作的度量。**常规宽事件回答“此请求表现如何？”（延迟、状态、令牌）。审计事件回答“谁试图做什么，以及是否获准？”同一条管道，不同的问题，这也是模式被保留且事件在采样后仍被强制保留的原因。
::

## 快速开始

你已经在使用 evlog 了。只需做三处改动即可添加审计日志：

```typescript [server/plugins/evlog.ts]
import { auditEnricher, auditOnly, signed } from 'evlog'
import { createAxiomDrain } from 'evlog/axiom'
import { createFsDrain } from 'evlog/fs'

export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('evlog:enrich', auditEnricher())
  nitro.hooks.hook('evlog:drain', createAxiomDrain())
  nitro.hooks.hook('evlog:drain', auditOnly(
    signed(createFsDrain({ dir: '.audit' }), { strategy: 'hash-chain' }),
    { await: true },
  ))
})
```

::

就是这样。审计事件：

- 与其余日志一样，经过同一条宽事件管道
- 在尾部采样后**始终保留**
- 写入你的主排出器（Axiom），**并且**写入一个专用的、已签名的、仅追加排出器（FS journal）
- 通过 `auditEnricher` 自动携带 `requestId`、`traceId`、`ip` 和 `userAgent`

::tip
**为什么需要两个排出器？**主排出器（Axiom、Datadog……）将审计日志与其余遥测数据放在一起，这样仪表板和查询仍然可用。已签名的排出器是你的保险：如果主排出器发生中断、数据被清除，或管理员悄悄删除某一行，FS journal 仍然保留这条链。审计员两者都需要：快速查询*和*防篡改凭证。
::

::audit-dual-sink
::

## 组合方式

每一层都是**可选接入并可替换**的。除了 `log.audit`、`auditEnricher` 以及 `auditOnly` / `signed` 之外，其他所有节点都与常规宽事件共享。
