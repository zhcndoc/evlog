evlog 每个请求增加 **约 3µs 的开销**，即 0.003ms，比任何 HTTP 框架或数据库调用都低几个数量级。

## evlog 与其他方案对比

所有基准测试均使用 JSON 输出到无操作目标。pino 写入 `/dev/null`（同步），winston 写入无操作流，consola 使用无操作报告器，evlog 使用静默模式。

### 结果

::bench-bar-race
::

| 场景 | evlog | pino | consola | winston |
|----------|------:|-----:|--------:|--------:|
| 简单字符串日志 | 1.83M ops/s | 1.09M | **2.79M** | 1.20M |
| 结构化（5 个字段） | 1.64M ops/s | 716.1K | **1.71M** | 431.6K |
| 深层嵌套日志 | **1.55M** ops/s | 464.9K | 1.01M | 164.0K |
| 子日志记录器／作用域日志记录器 | **1.70M** ops/s | 845.0K | 280.4K | 430.0K |
| 广泛事件生命周期 | **1.58M** ops/s | 205.8K | — | 111.9K |
| 突发（100 条日志） | 17.8K ops/s | 10.3K | **39.4K** | 7.5K |
| 日志记录器创建 | **16.85M** ops/s | 7.50M | 310.3K | 5.38M |

evlog 在 7 次一对一比较中赢了 **4 次**，而且最重要的胜利都很显著：在广泛事件模式下比 pino **快 7.7 倍**，日志创建 **快 2.3 倍**，深层嵌套日志 **快 3.3 倍**。consola 在简单字符串和突发场景中略胜一筹（它使用不做序列化的无操作报告器），但 evlog 为每个请求生成一条相关联事件，而传统日志记录器会发出 N 条独立日志行。

::callout{icon="i-lucide-info" color="info"}
**为什么这很重要**：在广泛事件模式（每个请求一个事件，也就是实际的 API 形态）下，evlog 比 pino 快 7.7 倍，比 winston 快 14.1 倍，同时发送一个可查询的事件，而不是 4 条互不关联的日志行。在下面的结账流程中，事件数量减少了 75%，字节数减少了 56%，因为级别、时间戳、主机和请求绑定信息不再在每一行中重复。7.7 倍的优势并不是蛮力取胜。pino 并不尝试累积上下文，因此这个比较体现的是架构差异，而不是公平性问题。有关客观存在的差距，请参阅[evlog 可能不会获胜的场景](#when-evlog-might-not-win)。
::

### 什么是“广泛事件生命周期”？

该基准测试模拟了一个真实的 API 请求：

::code-group
```typescript [evlog（1 个事件）]
const log = createLogger({ method: 'POST', path: '/api/checkout', requestId: 'req_abc' })
log.set({ user: { id: 'usr_123', plan: 'pro' } })
log.set({ cart: { items: 3, total: 9999 } })
log.set({ payment: { method: 'card', last4: '4242' } })
log.emit({ status: 200 })
```

```typescript [pino（4 条日志行）]
const child = pinoLogger.child({ method: 'POST', path: '/api/checkout', requestId: 'req_abc' })
child.info({ user: { id: 'usr_123', plan: 'pro' } }, 'user context')
child.info({ cart: { items: 3, total: 9999 } }, 'cart context')
child.info({ payment: { method: 'card', last4: '4242' } }, 'payment context')
child.info({ status: 200 }, 'request complete')
```
::

相同的 CPU 开销，但 evlog 将所有内容集中在一个位置。

## 为什么 evlog 更快？

上述数字并非魔法，源于深思熟虑的架构选择：

**原地修改，而非复制。** `log.set()` 通过递归的 `mergeInto` 函数直接写入上下文对象。其他日志记录器在每次调用时克隆对象（使用对象展开或 `Object.assign`）。evlog 在上下文累积过程中从不分配中间对象。

**直到输出阶段才序列化。** 上下文在整个请求生命周期中保持为普通 JavaScript 对象。`JSON.stringify` 仅在输出时运行一次。传统日志记录器在每次 `.info()` 调用时都进行序列化，4 条日志行意味着 4 次序列化。

**延迟分配。** 时间戳、采样上下文和覆盖对象仅在实际需要时创建。如果尾部采样被禁用（常见情况），其上下文对象就永远不会被分配。ISO 时间戳会缓存格式化后的秒前缀，每次调用时只追加毫秒（在秒数变化时失效），因此高频的 emit 路径无需每次都重新运行 `toISOString()`。

**一个事件，而不是 N 行。** 对于典型请求，pino 会发出 4 行或更多需要序列化、传输和索引的 JSON 日志。evlog 只发出一条。这意味着日志传输端的事件数量减少 75%，网络传输字节数减少 56%，并且只需查询一行而不是四行。[日志成本](/reference/cost)会根据你自己的流量计算相应费用。

**正则表达式缓存。** 全局模式（用于采样和路由匹配）只编译一次并缓存。重复评估命中缓存而非重新编译。

## 当 evlog 可能不会获胜时

上述基准测试测量的是主线程上的 CPU 和序列化开销，不涉及真实 I/O。这是 pino、winston 和 logtape 自己进行基准测试时采用的标准设置，但它遗漏了一些其他日志记录器可能略胜一筹的场景。以下是需要坦诚说明的情况：

**使用 pino 工作线程的即发即忘高频路径。** 在生产环境中，pino 通常配置了[工作线程传输](https://getpino.io/#/docs/transports)（`pino-pretty`、`pino-loki`、特定供应商的传输）。序列化和 I/O 完全移出主线程。对于每秒发出数十万条没有上下文累积的 `log.info('foo')` 日志行的工作负载，pino-via-worker 在主线程上可以达到约 2～3M ops/s，因为它实际上只是在排队。我们无法在单线程 vitest 进程中公平地测试这种模式，因此它没有出现在表格中，但这确实是 pino 更快的场景。

**不进行序列化的 CLI／仅美化输出。** 我们基准测试中的 consola 无操作报告器模式（`level: 4, reporters: [{ log: () => {} }]`）完全跳过了 JSON 序列化。如果你将 consola 用于仅向终端输出的 CLI，这种情况是现实的，但这也是 consola 在“简单字符串”和“突发”场景中胜出的原因：它没有执行相同的工作。evlog 和 pino 都会序列化为 JSON；[这些基准测试](#results)中的 consola 则不会。如果你的使用场景是“美化终端输出，不向任何地方发送日志”，consola 确实更轻量，这也是它在[简单字符串和突发行](#results)中领先的原因。

**单次 `log.info` 调用，不累积上下文。** 在 `pino.info('hello')` 与 `evlog.info('hello')` 的比较中，evlog 和 pino 大致相当（在我们的运行中分别为 1.83M 和 1.09M ops/s，但如果 pino 以异步模式运行，差距会进一步缩小）。evlog 约 7.7 倍的优势具体体现在：否则你需要为一个逻辑操作发出 N 行独立日志。如果你确实是每次调用记录一行且不累积上下文，那么速度差异会小得多。选择 evlog 是为了它的 API 易用性（`log.set` 加结构化错误），而不是原始吞吐量。

**墙上时钟时间的差异确实存在。** 在同一台机器上，不同运行之间的 Vitest 基准测试数字会变化 ±5～10%（受热降频、GC 和其他进程影响）。上面的数字来自 MacBook 上的一次运行，因此应将其视为快照，而不是保证的最低值。请在你关心的硬件上自行运行测试套件。

结论是：**广泛事件模式下的优势是真实的**，但如果你的技术栈是“使用[工作线程传输](https://getpino.io/#/docs/transports)的纯即发即忘 pino”，那是我们不声称能够胜出的唯一场景。

## 一个真实请求的成本

对于典型 API 请求：

| 组件 | 开销 |
|-----------|-----:|
| 日志记录器创建 | 52ns |
| 3 次 `set()` 调用 | 105ns |
| `emit()` | 400ns |
| 采样 | 22ns |
| 增强器管道 | 2.14µs |
| **总计** | **约 2.7µs** |

作为参考，数据库查询需要 1～50ms，HTTP 调用需要 10～500ms，因此这 2.7µs 比请求已经执行的最廉价操作还低三个数量级。

## 打包体积

每个入口点都支持 tree-shaking，因此项目只导入 `evlog` 时，只需为核心部分付费，不包含下表中的其他内容。

| 入口 | Gzip 体积 |
|-------|-----:|
| core (`evlog`) | 510 B |
| toolkit (`evlog/toolkit`) | 720 B |
| utils | 1.58 kB |
| error | 1.46 kB |
| enrichers | 1.99 kB |
| pipeline | 1.35 kB |
| http | 1.22 kB |
| browser | 289 B |
| workers | 1.30 kB |
| client | 128 B |

典型的 Node.js 包（`initLogger` + `createLogger`）在 tree-shaking 后端到端的体积约为 **6.3 kB gzip**；添加 `createRequestLogger`、`createError`、`parseError` 和 `useLogger` 后，包体积约为 **7.2 kB gzip**。适配器和框架集成构建于其之上：Hono 为 617 B，Express 为 734 B，Axiom 为 1.48 kB。

## 方法论与可信度

### 你能相信这些数字吗？

本页面上的每个基准测试都是**开源的**且**可复现的**。基准测试文件位于 [`packages/evlog/bench/`](https://github.com/hugorcd/evlog/tree/main/packages/evlog/bench)。你可以阅读确切代码、在本机运行并验证结果。

所有库在相同条件下测试：
- **相同输出模式**：JSON 输出到无操作目标（不测量磁盘或网络 I/O）
- **相同预热**：每个基准测试在 JIT 稳定后运行 500ms
- **相同工具**：[Vitest bench](https://vitest.dev/guide/features#benchmarking)，由 [tinybench](https://github.com/tinylibs/tinybench) 提供支持
- **相同机器**：比较库时，所有基准测试在同一进程的同一硬件上运行

### 自行运行

cd packages/evlog

pnpm run bench                          # 所有基准测试
pnpm exec vitest bench bench/comparison/ # 仅与替代方案对比
pnpm exec tsx bench/scripts/size.ts     # 包体积
