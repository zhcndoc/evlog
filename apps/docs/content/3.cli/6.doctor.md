`evlog doctor` 会回答“evlog 真的在这里接入了吗？”——当你按照设置指南操作后却什么都没有显示时，你会想问的就是这个问题。

```bash [Terminal]
evlog doctor
```

```text [Output]
pnpm workspace

ENVIRONMENT
│ ✓ node     v24.18.0
│ ✓ project  evlog-playground · pnpm · apps/playground
│ ✓ stack    nuxt

EVLOG
│ ✓ evlog  v2.22.3 (workspace:*)
│ ✓ logs   1 file · .evlog/logs

5 ok · 0 warn · 0 fail
```

## 检查内容

| 检查项 | 通过时 | 警告或失败时 |
| --- | --- | --- |
| `node` | Node 20 或更高版本 | 低于 20 — CLI 将无法可靠运行（失败） |
| `project` | 已解析到 `package.json` | 工作目录上方未找到任何文件 |
| `stack` | 已检测到框架且已安装 evlog | 已检测到框架，但 evlog 未接入该框架 |
| `evlog` | 已从 `node_modules` 解析到 `evlog` | 已在 `package.json` 中声明但未安装，或完全缺失 |
| `logs` | 存在本地 sink，或已接入 fs drain（该目录会在首次写入时出现） | 永不出现 — 未配置本地 sink 时会省略此项 |

在工作区中，标题会标明工作区类型，而 `project` 会显示解析到了哪个包——这是最快发现你是在诊断仓库根目录而不是应用本身的方法。

本地 sink 是可选的：[fs drain](/integrate/adapters/self-hosted/fs) 会将日志写入 `.evlog/logs` 下，并在首次写入时创建该目录，因此在产生任何事件之前，已接入的 drain 也会被视为 sink。未配置本地 drain 的项目完全不会进行 `logs` 检查。

## 退出代码

`0` 表示没有任何失败，`1` 表示任意检查失败。警告不会使命令失败——尚未写入日志的项目并不表示已损坏。

## JSON

```bash [Terminal]
evlog doctor --json | jq '.checks'
```

负载包含已解析的项目（`cwd`、`root`、`packageDir`、工作区类型、包名、检测到的技术栈），每一项检查及其状态，以及汇总计数。

每个警告和失败还会附带一个来自 CLI 自有错误目录的代码 — `cli.EVLOG_NOT_FOUND`、`cli.EVLOG_DECLARED_NOT_INSTALLED`、`cli.NODE_TOO_OLD`、`cli.PROJECT_NO_PACKAGE` — 每个代码都包含 `why` 和 `fix`，其工作方式与应用中的[结构化错误](/learn/structured-errors)相同。

## 选项

| 标志 | 功能 |
| --- | --- |
| `--cwd <dir>` | 诊断其他目录 |
| `--json` | 在标准输出中输出机器可读结果 |
| `--debug` | 打印命令执行经过的步骤 |
| `--noHeader` | 跳过品牌页眉 |
