[`node:diagnostics_channel`](https://nodejs.org/api/diagnostics_channel.html) 是运行时内置的检测发布/订阅机制。evlog 可以将每个宽事件发布到 `evlog.event` 通道，因此消费者只需通过通道名称进行订阅即可——无需导入 evlog，也无需在 `initLogger()` 中添加条目。

## 用途

以下两件事无法通过 [插件](/extend/plugins) 或 [排出器](/extend/custom-drains) 完成：

- **从不依赖 evlog 的软件包中发布 evlog 集成。** 订阅者只需要频道名称，因此供应商 SDK、内部共享库或 APM 代理无需对等依赖、版本约束，也无需在 `initLogger()` 调用中添加一行代码，即可消费宽事件。
- **无需排出器即可将事件从 Cloudflare Worker 中传出。** Workers 会将每条频道消息转发给 [Tail Worker](#cloudflare-workers)，它会在响应之后运行，并拥有独立的 CPU 配额——无需 `waitUntil`，也无需让排出器与请求争夺资源。

对于其他所有场景——批处理、重试、添加字段、将事件分发给多个进程内消费者——插件或排出器是更好的工具。本页底部有一个[插件更适用时的比较](#when-a-plugin-is-the-better-tool)。

## 启用它

默认情况下处于关闭状态。启动时启用一次：

```typescript
import { enableDiagnosticsChannel } from 'evlog/diagnostics'

await enableDiagnosticsChannel()
```

该调用不接受任何选项，在所有框架中的用法都相同——只有应用执行启动代码的*位置*不同：

::code-group
```typescript [Nuxt / Nitro]
// server/plugins/evlog-diagnostics.ts
import { enableDiagnosticsChannel } from 'evlog/diagnostics'

export default defineNitroPlugin(async () => {
  await enableDiagnosticsChannel()
})
```

```typescript [Next.js]
// instrumentation.ts
import { defineNodeInstrumentation } from 'evlog/next/instrumentation'

export const { register, onRequestError } = defineNodeInstrumentation(async () => {
  const { createInstrumentation } = await import('evlog/next/instrumentation/create')
  const { enableDiagnosticsChannel } = await import('evlog/diagnostics')
  const { register: evlogRegister, onRequestError } = createInstrumentation({ service: 'my-app' })

  return {
    async register() {
      await evlogRegister()
      await enableDiagnosticsChannel()
    },
    onRequestError,
  }
})
```

```typescript [SvelteKit]
// src/hooks.server.ts
import { createEvlogHooks } from 'evlog/sveltekit'
import { enableDiagnosticsChannel } from 'evlog/diagnostics'

await enableDiagnosticsChannel()

export const { handle, handleError } = createEvlogHooks()
```

```typescript [Hono]
// Express、Fastify、Elysia、NestJS 和 oRPC 的用法相同：
// 在服务器入口中启用一次，并在应用开始处理请求之前完成。
import { Hono } from 'hono'
import { evlog } from 'evlog/hono'
import { enableDiagnosticsChannel } from 'evlog/diagnostics'

await enableDiagnosticsChannel()

const app = new Hono()
app.use(evlog())
```

```typescript [Cloudflare Workers]
// src/worker.ts — 需要 nodejs_compat 标志
import { initWorkersLogger, withEvlog } from 'evlog/workers'
import { enableDiagnosticsChannel } from 'evlog/diagnostics'

initWorkersLogger({ env: { service: 'my-worker' } })
await enableDiagnosticsChannel()

export default withEvlog(async (request, env, ctx, log) => {
  log.set({ action: 'handle_request' })
  return Response.json({ ok: true })
})
```

```typescript [Standalone]
// 任意 Node、Bun 或 Deno 入口点
import { initLogger } from 'evlog'
import { enableDiagnosticsChannel } from 'evlog/diagnostics'

initLogger({ env: { service: 'worker' } })
await enableDiagnosticsChannel()
```
::

`enableDiagnosticsChannel()` 是异步的，因为它会延迟加载 `node:diagnostics_channel`——这正是让该内置模块不进入 Convex、workerd 及其他非 Node 目标环境主构建包的原因。在 promise 完成之前发出的事件不会被发布，因此应在启动时调用它，而不是在请求内部调用。入口点无法使用顶层 `await` 的框架，应在调用 `initLogger()` 的同一位置调用它，并在那里等待其完成。

::callout{icon="i-lucide-info" color="info"}
这是一个观测旁路，而不是传输机制。订阅者会同步运行，且不会被等待——没有批处理、重试或 `waitUntil`。如需将事件传送到后端，请使用 [排出器](/extend/custom-drains)；两者会看到相同的事件。
::

## 订阅

该频道的要点是，消费者除了频道名称外，不需要从 evlog 获取任何内容：

```typescript [metrics.ts]
import { channel } from 'node:diagnostics_channel'

/** 发布的消息。在本地声明，因此此文件无需导入 evlog。 */
type EvlogMessage = { event: Record<string, unknown> & { level: string; service: string } }

channel('evlog.event').subscribe((message) => {
  const { event } = message as EvlogMessage
  if (event.level === 'error') metrics.increment('errors', { path: String(event.path ?? 'unknown') })
})
```

Node 会将发布的消息类型标记为 `unknown`，因此请在处理程序顶部将其缩小一次。使用 `channel(name).subscribe()` 而不是模块级别的 `subscribe()`，是因为前者存在于 evlog 支持的每个 Node 版本中。

如果你已经依赖 evlog，并希望为载荷添加类型：

```typescript [alerts.ts]
import { subscribeToWideEvents } from 'evlog/diagnostics'

const stop = await subscribeToWideEvents((event) => {
  //                                       ^? WideEvent
  if (typeof event.status === 'number' && event.status >= 500) {
    alerts.push({ path: String(event.path ?? '-'), requestId: String(event.requestId ?? '-') })
  }
})
```

[基础事件](/learn/wide-events)之外的字段类型为 `unknown`，而在请求之外发出的事件完全不包含 HTTP 字段——请在使用前进行类型缩小，不要直接进行类型转换。

## 订阅者收到的内容

与 drain 收到的是同一个对象：经过审计、脱敏和增强之后的对象。请求包含所有增强器添加的内容——地理位置、用户代理、追踪上下文：

```json
{
  "timestamp": "2026-08-02T10:23:45.612Z",
  "level": "error",
  "service": "checkout",
  "environment": "production",
  "method": "POST",
  "path": "/api/checkout",
  "status": 500,
  "duration": "1.20s",
  "requestId": "4a8ff3a8-...",
  "user": { "id": "usr_123", "plan": "premium" },
  "error": { "name": "PaymentDeclined", "message": "Card declined" }
}
```

在请求之外发出的事件（`log.info({ ... })`、`createLogger().emit()`）到达时不包含 HTTP 字段，而来自 `log.fork()` 的事件则会携带 `operation` 和 `_parentRequestId`。

::callout{icon="i-lucide-triangle-alert" color="warning"}
该事件是实时对象，而不是副本——修改它会同时修改 drain 收到的内容。请将其视为只读对象。此外，抛出异常的订阅者**不会被隔离**：`Channel.publish()` 会在下一个 tick 将异常重新抛出为未捕获异常，而这在大多数应用中都是致命的。请确保订阅者能够处理所有情况。
::

在 pretty 模式（开发环境默认模式）下，像 `log.info('auth', 'User logged in')` 这样的带标签日志会直接写入控制台，永远不会成为宽事件，因此不会出现在 channel 上。宽事件本身在两种模式下都会发布。

## 你可以构建的内容

### 不依赖 evlog 的集成

订阅的包只需要频道名称，不需要其他任何内容——不依赖 `evlog`，不需要保持同步的 peer 范围，宿主应用中除了导入它之外也不需要进行额外连接：

```typescript [acme-apm/src/evlog.ts]
import { channel } from 'node:diagnostics_channel'

type EvlogMessage = {
  event: Record<string, unknown> & { timestamp: string; level: string; service: string }
}

channel('evlog.event').subscribe((message) => {
  const { event } = message as EvlogMessage

  acme.ingest({
    at: event.timestamp,
    level: event.level,
    service: event.service,
    attributes: event,
  })
})
```

```typescript [宿主应用]
import 'acme-apm/evlog'
```

同样的形式也适用于跨服务共享的内部库：一个包负责订阅，每个导入它的服务都会上报，而且它们都不需要接触 `initLogger()`。

### 在应用旁边统计计数并设置告警

订阅者就是一个普通函数，因此所有能在进程内计算的内容都可以在这里计算——同时不会占用用于将事件发送到后端的排空槽位：

```typescript [observability.ts]
import { channel } from 'node:diagnostics_channel'

const errorsByPath = new Map<string, number>()

channel('evlog.event').subscribe((message) => {
  const { event } = message as { event: Record<string, unknown> & { level: string } }
  if (event.level !== 'error') return

  const path = String(event.path ?? 'unknown')
  errorsByPath.set(path, (errorsByPath.get(path) ?? 0) + 1)

  if (typeof event.status === 'number' && event.status >= 500) {
    void pager.notify(`5xx on ${path}`, { requestId: event.requestId })
  }
})

export function errorCounts(): Record<string, number> {
  return Object.fromEntries(errorsByPath)
}
```

[插件](/extend/plugins)也可以完成同样的工作；当代码位于你自己的应用中时，这是更好的选择。当订阅者作为独立包发布，或必须在不编辑应用日志配置的情况下附加时，频道则更具优势。

## Cloudflare Workers

Workers 会将每条诊断通道消息转发到 [Tail Worker](https://developers.cloudflare.com/workers/observability/logs/tail-workers/)。在 Worker 中启用该通道后，宽事件会在无需 drain、无需 `waitUntil` 且拥有独立 CPU 配额的情况下离开隔离环境——Tail Worker 负责发送，并且此时响应已经返回：

```typescript [tail-worker/index.ts]
export default {
  async tail(events) {
    for (const event of events) {
      for (const messageData of event.diagnosticsChannelEvents) {
        if (messageData.channel !== 'evlog.event') continue

        await fetch('https://logs.example.com/ingest', {
          method: 'POST',
          headers: { 'Content-Type': 'application/json' },
          body: JSON.stringify(messageData.message.event),
        })
      }
    }
  },
}
```

每个条目都包含 `timestamp`、`channel` 和 `message`——其中 `message` 就是 evlog 发布的内容，因此宽事件位于 `messageData.message.event`。需要启用 `nodejs_compat` 标志；消息会经过结构化克隆算法，因此只有可克隆的值才能保留。

## 插件是更好工具的情况

该通道并不是 [插件](/extend/plugins) 的替代方案——它有意保持了更窄的范围：

| 你想要…… | 使用 |
| --- | --- |
| 将事件发送到后端，并进行批处理和重试 | [自定义 drain](/extend/custom-drains) |
| 在事件被 drain 之前为其添加字段 | [Enricher](/extend/custom-enrichers) 或插件 |
| 将事件分发给多个进程内消费者 | 插件——`initLogger({ plugins: [a, b, c] })` 已经支持此功能 |
| 从必须依赖 evlog 的包中订阅 | 此通道 |
| 在没有 drain 的情况下从 Cloudflare Worker 中导出事件 | 此通道 |

`diagnostics_channel` 运行在进程内：外部无法连接到正在运行的进程。无论如何，订阅者的代码都必须由你的应用加载——该通道只是让你少写一行配置，而不是免除依赖。
